축잘알 기술 명세

유럽 4대 리그 승부 예측 게임. 이 문서는 웹(JS)·Android·iOS 세 클라이언트와 공용 백엔드가 공유하는 규칙을 정의한다. 핵심은 2장의 점수 공식이며, 나머지는 그것을 실어 나르는 구조다.

웹 · React Android · Compose iOS · SwiftUI EPL · 라리가 · 분데스리가 · 세리에A
01

제품 원칙

모든 설계 판단은 이 네 가지로 되돌아가서 검증한다.

01

맞췄나가 아니라, 얼마나 알았나

쉬운 경기를 맞히는 것과 어려운 경기를 맞히는 것은 같은 값일 수 없다. 점수는 적중 여부가 아니라 기준선 대비 정보 이득으로 잰다.

02

확신에는 대가가 따른다

확신도를 올리면 맞았을 때 크게 얻지만 틀렸을 때 크게 잃는다. 모두가 최고 확신을 누르는 순간 확신은 정보가 아니게 된다.

03

실력과 성실함을 분리한다

축잘알 지수는 오르내리는 실력 지표(상위 %의 근거), 포인트는 절대 줄지 않는 활동 지표(레벨의 근거). 못 맞혀도 레벨은 오른다.

04

도박이 아니다

배당률, 금전 보상, 마감 초읽기 연출을 쓰지 않는다. 우리가 파는 감정은 ‘딴다’가 아니라 ‘내가 봤지?’다.

02

점수 시스템

이 게임의 전부다. 목표는 하나 — 어려운 경기를 확신을 갖고 맞히는 사람이 압도적으로 높은 점수를 받고, 그 확신을 함부로 쓰면 손해를 보게 만든다.

2.1 예측 입력

유저는 두 가지를 고른다. 승부 예측 하나와 확신도 하나.

입력값UI 표현
pickHOME / DRAW / AWAY보기 3개 중 하나
confidence1 / 2 / 3감이 와요 / 꽤 확신해요 / 이건 확실해요

예측 창 — 경기 당일에만 연다

예측은 매치데이가 열린 경기에만 가능하다. 마감은 킥오프 5분 전이고, 그 사이에는 몇 번이든 수정할 수 있다. 마감 판정은 항상 서버 시각 기준이다.

결정

매치데이는 자정이 아니라 KST 06:00에 시작한다. 유럽 경기는 한국 시간 새벽에 열린다. 자정으로 하루를 자르면 토요일 밤에 ‘일요일 새벽 4시 경기’를 예측할 수 없고, 예측 창이 새벽 0시~4시의 네 시간으로 쪼그라든다. 06:00 경계로 자르면 토요일 아침부터 일요일 새벽 경기까지 한 매치데이 22시간이 이어져 한국 축구팬의 체감과 맞는다. 서버에서는 fixtures.opens_at에 저장하고 RLS가 이 창을 강제한다.

2.2 기준선 q — 이 경기가 얼마나 어려운가

경기마다 세 결과에 대한 기준 확률 q = [q_home, q_draw, q_away]를 만든다. 이것이 난이도의 정의다. q가 낮은 결과를 맞히면 점수가 크다.

q = w · qmodel + (1 − w) · qcrowd,   w = 30 / (30 + N)
N = 마감 시점 예측 참여자 수. 참여가 적으면 모델을, 많아지면 집단지성을 신뢰한다.
  • q_model — 팀 Elo, 최근 5경기 폼, 홈 어드밴티지, 리그별 무승부 기저율로 산출. 초기에는 데이터 제공사의 암시 확률을 그대로 써도 된다.
  • q_crowd — 마감 시점 유저 예측 분포에 라플라스 스무딩: (n_i + 1) / (N + 3). 본인 예측은 제외(leave-one-out)해서 자기 점수를 자기가 흔들지 못하게 한다.
  • 최종 q는 [0.03, 0.94]로 클램프 후 합이 1이 되도록 정규화한다.
결정

q는 마감 시각에 동결(freeze)되어 fixture_baselines에 저장된다. 늦게 예측한 사람이 분포를 보고 유리해지는 것을 막고, 정산을 결정론적·재현 가능하게 만들기 위해서다. 정산 로직은 순수 함수여야 한다.

2.3 확신도를 확률로 번역하기

확신도는 절대 확률이 아니라 “기준선에서 내 픽 쪽으로 얼마나 이동하는가”로 해석한다.

ppick = qpick + c · (1 − qpick),   c ∈ { 0.15, 0.35, 0.60 }
나머지 확률 질량 (1 − ppick)은 다른 두 결과에 q 비율대로 분배한다.

왜 절대 확률이 아닌 상대 이동인가. 확신도를 고정 확률(예: 확신1 = 40%)로 두면, 다수 의견을 낮은 확신으로 골랐을 때 맞히고도 점수가 깎이는 상황이 생긴다. 유저 입장에서 납득 불가능한 경험이다. 상대 이동 방식은 맞히면 항상 이득, 틀리면 항상 손해를 보장한다.

2.4 지수 변동 — 로그 스코어

실제 결과가 나오면, 그 결과에 유저가 부여했던 확률을 기준선과 비교한다.

Δ지수 = round( K · log₂( p(실제결과) / q(실제결과) ) ),   K = 40
clamp [−60, +90] 적용. 단위는 비트(bit) — 기준선 대비 이 경기에 대해 당신이 더 알고 있던 정보량.

예측 대회(Good Judgment Project, Metaculus)가 쓰는 적정 채점 규칙(proper scoring rule)이다. 성질이 하나 있는데, 이게 이 게임의 핵심 안전장치다 — 자기 확신을 정직하게 말하는 것이 기대 점수를 최대화한다. 부풀리면 손해다. (검증은 2.6)

표 하나가 이 게임의 설계를 다 설명한다. 다수 의견에 최고 확신을 걸면 +18, 소수 의견에 최고 확신을 걸어 맞히면 +79. 네 배가 넘는다. 그런데 둘 다 틀렸을 때의 손해는 −53으로 똑같다. 안전하게 가는 사람은 지수가 거의 오르지 않고, 볼 줄 아는 사람만 치고 올라간다.

틀렸을 때의 손해가 확신도에만 의존하는 이유. 남은 확률 질량을 q 비율대로 나눴기 때문에 p_wrong / q_wrong이 어떤 오답이든 동일해진다. 결과적으로 틀리면 확신도에 따라 −9 / −25 / −53로 딱 떨어진다. 유저에게 설명하기 쉽고, 예측 화면에서 미리 보여줄 수 있다.

2.8 포인트 — 절대 줄지 않는 쪽

포인트 = max(0, Δ지수) + 3 + min(연속적중, 10) × 2
참여 보너스 3점은 틀려도 지급한다. 포인트는 레벨의 근거이므로 하락하지 않는다.

지수는 실력을 재기 위해 떨어져야 하고, 레벨은 계속 놀게 만들기 위해 떨어지면 안 된다. 두 개를 분리한 이유가 이것이다.

03

지수 · 레벨 · 티어

세 지표가 각각 다른 질문에 답한다. 목업의 Lv.12 마스터 · 상위 3.1%는 이 셋을 한 줄에 표시한 것이다.

지표답하는 질문근거하락범위

3.1 지수

  • 시즌 시작값 1000. 경기마다 Δ지수를 더한다.
  • 상위 %는 같은 시즌에 20경기 이상 예측한 유저 안에서의 백분위. 표본이 적은 유저가 상위권을 오염시키는 것을 막는다.
  • 시즌 종료 시 1000 + (지수 − 1000) × 0.6으로 소프트 리셋. 상위권을 완전히 밀지 않으면서 신규 유저에게 기회를 준다.

3.2 레벨

다음 레벨까지 필요 포인트 = 100 + 25 × (L − 1)
Lv.12 도달 = 누적 2,475 포인트. 하루 3경기 예측 기준 약 45일 — 한 시즌의 호흡.

3.3 티어

절대값이 아니라 백분위로 나눈다. 유저 수가 늘어도 자동으로 균형이 맞고, “상위 몇 %”라는 이 게임의 정체성과 직결된다. 매일 04:00 KST 재계산.

배치(placement) 20경기를 둔다. 신규 유저가 운으로 상위 1%에 뜨는 것을 막고, 초반 20경기 자체가 하나의 목표가 된다. 배치 중에는 랭킹에 노출되지 않고 “앞으로 n경기”만 보인다.

04

포인트 경제

포인트는 어디서 나오고 어디로 사라지는가. 이 절이 없으면 포인트는 레벨 옆에 붙은 죽은 숫자가 된다.

4.1 포인트는 두 개다

하나의 이름 아래 성격이 다른 두 값을 관리한다. 획득 이벤트가 발생하면 둘 다 증가하고, 상점에서 쓰면 보유만 감소한다.

값쓰임감소표시 위치
누적 포인트 lifetime레벨 산정절대 없음레벨 게이지
보유 포인트 balance상점 구매있음상점 헤더, 내 기록
결정

레벨은 누적 포인트로만 계산한다. 상점에서 썼다고 레벨이 내려가면 아무도 사지 않는다. 이 분리를 안 하면 상점을 여는 순간 경제가 무너진다.

4.4 미션 설계 원칙

미션은 포인트 공급의 조절 밸브이자, 유저 행동을 유도하는 유일한 레버다. 그만큼 잘못 쓰면 게임의 핵심 데이터를 오염시킨다.

이런 미션을 만든다

서로 다른 두 리그에서 예측하기 · 경기 채팅에 참여하기 · 예측 근거 한 줄 쓰기 · 이번 주 7경기 예측하기

모두 행동의 다양성을 유도하고 결과 운에 의존하지 않는다.

절대 만들지 않는다

“확신3으로 예측하기” — 확신 신호를 직접 오염시킨다
“오늘 경기 전부 예측하기” — 생각 없는 예측을 유도해 q_crowd를 망친다
적중을 요구하는 데일리 미션 — 운을 매일 강요한다 (위클리 1개까지만 허용)

결정

미션 보상은 포인트만 준다. 지수에는 어떤 경우에도 영향을 주지 않는다. 지수는 실력 지표이므로 성실함으로 살 수 없어야 한다.

4.5 소비 — 상점

포인트를 쓸 곳이 없으면 미션도 스트릭도 동기가 되지 않는다. 상점은 필요하다. 다만 파는 물건에 한 가지 규칙이 있다.

원칙

코스메틱만 판다. 예측 정확도·점수·랭킹에 영향을 주는 상품은 어떤 형태로도 팔지 않는다. 지수가 돈이나 성실함으로 살 수 있게 되는 순간 “상위 3.1%”라는 이 앱의 유일한 자산이 무의미해진다.

상품가격비고
닉네임 컬러300 ~ 800채팅에도 적용
프로필 프레임800 ~ 2,500티어 엠블럼과 조합
채팅 말풍선 스킨500 ~ 1,500경기 채팅에서 눈에 띈다

팔지 않는 것

예측 변경권 · 마감 연장권 · 전문가 분석 열람 · 지수 하락 방어권 · 확신도 상향권 · 스트릭 복구권. 전부 “돈으로 실력을 사는” 상품이며 하나라도 열면 나머지를 막을 명분이 사라진다.

4.6 인플레이션 관리

  • 포인트는 현금으로 구매할 수 없다. 유일한 공급원은 플레이다. (수익화가 필요해지면 광고 제거·시즌 패스로 풀되, 시즌 패스 보상도 코스메틱으로 제한한다.)
  • 시즌이 끝나도 보유 포인트는 전액 이월한다. 대신 매 시즌 새 한정 상품을 내서 잉여를 흡수한다.
  • 감시 지표: 유저당 보유 포인트 중앙값 ÷ 현재 시즌 상품 총가격. 이 값이 1.5를 넘으면 공급 과잉 — 신규 상품을 추가하거나 미션 보상을 낮춘다.

조절은 미션 보상값으로만 한다. 공급이 과해도 정산 공식의 K나 c는 건드리지 않는다. 그건 경제 파라미터가 아니라 실력 측정 단위이고, 바꾸는 순간 과거 지수와 비교가 불가능해진다.

4.7 원장

포인트의 모든 증감은 원장을 통과한다. 잔액은 원장 합계와 항상 일치해야 하고, 어긋나면 알람을 띄운다.

// point_ledger — append only
{
  "id", "userId",
  "source": "settlement" | "streak" | "mission" | "onboarding"
           | "referral" | "season_bonus" | "purchase",
  "amount": 82,              // 소비는 음수
  "refType": "prediction", "refId": 1183042,
  "balanceAfter": 1322,
  "idempotencyKey": "settle:1183042",
  "createdAt"
}

구매와 정산 모두 멱등키를 요구한다. 정산 잡 재실행이나 결제 중복 탭으로 포인트가 두 번 들어가는 사고가 이 재화에서 가장 흔한 장애다.

최애 팀과 리그

5.1 가입 흐름

  1. 리그 선택 — 4개 중 1개 이상. 선택한 순서가 곧 탭 순서가 된다.
  2. 최애 팀 1개 — 선택한 리그의 팀 목록에서. 건너뛸 수 있지만, 개인화의 대부분이 여기서 나온다.
  3. 관심 팀 최대 5개 — 리그 무관.
  4. 알림 — 최애 팀 경기 예고, 정산 결과, 랭킹 변동.
// user_preferences
{
  "leagueOrder": [39, 140, 78, 135],   // EPL, 라리가, 분데스, 세리에A
  "favoriteTeamId": 42,              // 아스날
  "followedTeamIds": [50, 541],
  "notify": { "kickoff": true, "settlement": true, "rank": false }
}

5.2 리그 순서 변경

설정에서 드래그로 정렬하고 서버에 저장한다. 세 클라이언트가 같은 배열을 받아 같은 순서로 탭을 그린다. 선택하지 않은 리그는 배열 뒤쪽에 회색으로 붙어 언제든 켤 수 있다.

5.3 내 팀 경기는 다르게 보인다

위치차이
홈 피드날짜 섹션보다 위에 “내 팀 경기” 섹션 고정
경기 카드상단에 팀 컬러 4px 밴드, 엠블럼 확대, 내 팀 칩
알림킥오프 24시간 전 / 2시간 전 (미예측 상태일 때만)
경기 채팅닉네임 옆에 팀 컬러 점 — 어느 편 팬인지 보인다
정산결과 알림 문구가 팀 이름을 부른다
결정

최애 팀 경기라고 해서 점수 규칙을 바꾸지 않는다. 보너스를 주면 랭킹의 공정성이 무너지고, 페널티를 주면 팬을 벌주는 게임이 된다. 차이는 노출과 통계에서만 만든다.

5.4 팬심 편향 지수

대신 훨씬 재미있는 걸 준다. 팬은 자기 팀을 과대평가한다 — 이건 측정 가능한 사실이고, 측정하면 콘텐츠가 된다.

팬심 편향 = 최애팀 경기 평균 Δ지수 − 전체 평균 Δ지수
최애 팀 경기 10건 이상 쌓였을 때만 프로필에 노출한다.

음수일 때

“아스날 경기에서 평균 12점을 손해 보고 있어요. 다른 경기에서는 잘 보시는데요.”

양수일 때

“내 팀 경기에서 더 잘 맞히는 드문 유형. 냉정한 팬 뱃지를 받았어요.”

확신도별 실제 적중률(캘리브레이션 곡선)도 같은 화면에 둔다. 확신3의 실제 적중률이 60%라면 “당신은 확신을 20%p 부풀리고 있습니다”라고 말해줄 수 있다. 이 피드백이 유저를 실제로 더 나은 예측가로 만든다 — 그게 이 앱의 리텐션 논리다.

API

REST /v1 + 단일 WebSocket. 세 클라이언트가 동일한 계약을 쓴다. 인증은 Bearer 액세스 토큰(15분) + 리프레시 토큰(60일).

피드와 경기

GET/v1/feed?date=2026-09-02내 리그 순서대로 정렬된 경기 목록
GET/v1/fixtures/{id}라인업, 분포, 내 예측
GET/v1/fixtures/{id}/distribution현재 크라우드 분포

예측

PUT/v1/predictions/{fixtureId}생성·수정 (멱등)

// PUT /v1/predictions/1183042
{ "pick": "AWAY", "confidence": 3 }

// 200 OK — 마감 전이므로 잠재 점수를 함께 돌려준다
{
  "pick": "AWAY", "confidence": 3,
  "lockAt": "2026-09-02T03:55:00Z",
  "preview": { "ifCorrect": 79, "ifWrong": -53, "basedOn": "live" }

// 409 PREDICTION_LOCKED — 마감 이후

preview.basedOn: "live"는 아직 동결 전 값이라는 뜻이다. 클라이언트는 이 값을 “예상”으로 표기하고, 마감 후에는 동결된 값으로 갱신한다.

09

정산 파이프라인

모든 점수는 서버에서만 계산한다. 클라이언트의 계산은 미리보기 용도이며 신뢰하지 않는다.

단계시점작업
1킥오프 − 5분예측 마감. q 계산 후 fixture_baselines에 동결.
2경기 중10분마다 결과 확인. 열려 있고 아직 안 끝난 경기가 없으면 외부 API를 호출하지 않는다.
3종료 후 ~5분결과 확정 대기 후 수집. 정규 90분 결과 기준(연장·승부차기 제외).
4정산 잡예측별 p 계산 → Δ지수 → 포인트 → settlements 기록.
5정산 직후지수·레벨 갱신, 뱃지 규칙 평가, 스트릭 갱신.
6+1분푸시 발송, WS settlement.completed.
7매일 04:00 KST전체 백분위·티어 재계산, rating_history 스냅샷.
결정

정산은 멱등해야 한다. (prediction_id)에 유니크 제약을 걸고, 재실행 시 기존 행이 있으면 건너뛴다. 경기 결과 정정(오심 번복, 몰수 등)은 정산 취소 후 재정산하는 별도 관리자 작업으로 처리한다.

10

실시간 채팅

채널수명보존
league:{id}상시7일
match:{id}킥오프 −1시간 ~ +4시간24시간
결정

채팅은 별도 탭이 아니라 경기 안에만 있고, 킥오프 1시간 전에 열린다. 상시 열어두면 대부분의 방이 비어 있어 “지금 누가 보고 있다”는 느낌이 살지 않는다. 경기 직전으로 창을 좁히면 같은 시간에 사람이 모인다 — 이 앱에서 채팅의 가치는 정보가 아니라 동시성이다. 닫는 시각은 킥오프 +4시간(경기 2시간 + 여유 2시간)으로, 종료 직후의 대화까지 담고 잠근다.

창 판정은 RLS 정책이 강제한다(14.2와 같은 원칙). 클라이언트에서만 막으면 API를 직접 호출해 뚫을 수 있고, 그러면 아무도 없는 시간대에 스팸이 쌓인다.

  • WebSocket + Redis Pub/Sub. 경기 채널은 fixture_id 해시로 샤딩한다.
  • 메시지에 발화자의 티어와 상위 %를 함께 실어 보낸다 — 채팅에서 누구 말을 믿을지 판단하는 근거가 되고, 이게 이 앱 채팅의 차별점이다.
  • 레이트 리밋 5초당 3건. 가입 24시간 미만 계정은 슬로우 모드(30초당 1건).
  • 신고·차단·금칙어 필터. 신고 3건 누적 시 자동 숨김 후 검토 큐.
  • 메시지 본문 최대 300자, 링크 자동 차단(초기), 이미지 없음.
  • 리그 채널(league:{id})은 상시 열려 있다. 특정 시각에 모일 이유가 없는, 잡담과 정보 공유용 공간이다.

경기 중 스코어 언급은 필터링하지 않는다. 라이브 채팅이 존재 이유이므로 스포일러 보호는 의도적으로 포기한다. 대신 “아직 안 본 경기” 채널에는 들어가지 않도록 진입 시 한 번 안내한다.

대응

14.2 RLS — 점수는 클라이언트가 만질 수 없다

클라이언트가 Postgres에 직접 붙는 구조이므로, 12.2의 어뷰징 대응 대부분이 RLS 정책 문제로 바뀐다. 원칙은 하나다 — 점수가 붙는 테이블은 클라이언트에게 쓰기 정책을 아예 만들어 주지 않는다.

-- 예측: 본인 것만, 그리고 마감 전에만
create policy "insert before lock" on predictions
  for insert with check (
    auth.uid() = user_id
    and exists (select 1 from fixtures f
                 where f.id = fixture_id and now() < f.lock_at)
  );

-- 수정도 같은 조건. 마감 판정은 서버(DB) 시각이 유일한 기준이다.
create policy "update before lock" on predictions
  for update using (auth.uid() = user_id)
  with check (exists (select 1 from fixtures f
                       where f.id = fixture_id and now() < f.lock_at));

-- settlements · ratings · point_ledger : RLS만 켜고 쓰기 정책을 만들지 않는다.
-- 정책이 없으면 기본 거부이고, 정산 함수는 service_role로 RLS를 우회한다.
alter table settlements  enable row level security;
alter table point_ledger enable row level security;
create policy "read own ledger" on point_ledger
  for select using (auth.uid() = user_id);

예측 테이블에 점수 컬럼을 두지 않는다. delta_rating, points는 전부 settlements에만 존재한다. 클라이언트가 쓸 수 있는 테이블에 점수 컬럼이 하나라도 있으면 RLS를 아무리 조여도 언젠가 새어 나간다.

14.3 정산은 Postgres 함수로 쓴다

Edge Function(TypeScript)이 아니라 DB 함수로 쓰는 이유는 명세 9장이 요구한 두 가지 때문이다 — 멱등성과 원장 정합성. 한 트랜잭션 안에서 처리하면 둘 다 공짜로 따라온다. TypeScript로 짜면 부분 실패를 직접 다뤄야 한다.

-- 핵심 한 줄: 로그 스코어가 SQL에 그대로 있다
greatest(-60, least(90, round(40 * log(2, p_user[actual] / q[actual]))))::int

-- 한 트랜잭션: settlements → ratings → point_ledger
with delta as (...),
ins as (
  insert into settlements (prediction_id, q_snapshot, p_user, actual, delta_rating, points)
  select id, to_jsonb(q), to_jsonb(p_user), actual, d,
         greatest(0, d) + 3 + streak_bonus(user_id)
    from delta
  on conflict (prediction_id) do nothing      -- 재실행해도 안전
  returning *
)
insert into point_ledger (user_id, source, amount, ref_type, ref_id, idempotency_key)
select user_id, 'settlement', points, 'prediction', prediction_id,
       'settle:' || prediction_id
  from ins
on conflict (idempotency_key) do nothing;

DB 안에서 도는 작업(마감·정산·랭킹)은 API 비용이 없으므로 1분마다 돌린다. 외부 API를 쓰는 수집만 주기를 크게 벌린다 — 일정은 주 1회, 결과는 10분마다, 그나마도 열려 있는 경기가 없으면 호출하지 않는다(12.1). pg_cron이 Edge Function을 부를 때는 pg_net을 쓰고, 키는 Vault에 넣는다.

14.4 실시간은 Broadcast로 — Postgres Changes를 쓰면 안 된다

이 절이 이 장에서 제일 중요하다. Postgres Changes는 구독자 한 명마다 권한 검사를 반복하고, 순서 보존을 위해 단일 스레드로 처리한다. 처리량이 쓰기 속도가 아니라 구독자 수에 따라 떨어지고, 컴퓨트를 키워도 나아지지 않는다. 공식 문서도 같은 변경에 구독자가 3,000명을 넘으면 Broadcast를 쓰라고 안내한다.

우리는 인기 경기 하나에 1,800명 이상이 같은 채널을 본다. Postgres Changes로 짜면 평소에는 멀쩡하다가 가장 중요한 경기에서만 채팅이 밀린다 — 최악의 실패 방식이다.

create trigger broadcast_message after insert on chat_messages
  for each row execute function realtime.send(
    to_jsonb(new), 'chat.message', 'match:' || new.fixture_id, false

레이트 리밋(5초 3건, 신규 계정 슬로우 모드)은 insert 앞단의 before 트리거에서 막는다. 클라이언트 검증에 의존하지 않는다.

14.5 인증 — 토스 로그인 브리지

Supabase의 서드파티 인증은 비대칭 서명(RS256)과 OIDC 디스커버리 URL을 요구하고 HS256 대칭키는 지원하지 않는다. 토스가 그 형태로 토큰을 주면 브리지 없이 바로 연결되지만, 아니라면 토큰 교환 레이어가 필요하다.

// Edge Function: POST /auth/toss
토스 앱 → 미니앱에 토스 토큰 전달
  → 1. 토스 API로 토큰 검증, 사용자 식별자 획득
    2. users upsert (service_role)
    3. Supabase JWT 발급 (프로젝트 시크릿 서명, sub = user_id)
  → 클라이언트: createClient(url, anonKey, { accessToken: () => jwt })

JWT 서명 시크릿과 service_role 키는 Edge Function 안에서만 존재해야 한다. 미니앱 번들에 들어가는 순간 누구나 임의의 유저로 서명할 수 있고, 그러면 랭킹 전체가 무의미해진다. 리프레시 토큰 회전도 직접 구현해야 한다.

14.6 Supabase가 해주지 않는 것

  • 푸시 알림 — FCM / APNs, 앱인토스에서는 토스 알림 API. 정산 후 발송은 Edge Function에서 호출한다.
  • 30초 미만 스케줄 — pg_cron 최소 1분 (14.3에서 완화 결정).
  • 무료 플랜은 1주 미사용 시 일시정지 — 시즌 오프 기간이 존재하는 서비스라 Pro 플랜이 전제다.

14.8 확인이 필요한 것

  1. 앱인토스의 3,000 req/min이 미니앱 → 외부 API(Supabase) 호출에도 적용되는가. 적용된다면 화면마다 PostgREST를 여러 번 부르는 구조가 위험하다 — 피드는 RPC 한 번으로 묶고 나머지는 Realtime으로 받는다. 어느 쪽이든 이 설계가 안전하므로 확인 전에도 그렇게 만든다.
  2. 토스 로그인 토큰이 RS256 + OIDC 디스커버리를 제공하는가. 제공되면 14.5의 브리지가 통째로 사라진다.
